= Structured Text Components

// Custom lang highlight
// must come after the doc title, to work around a bug in asciidoc 8.6.6

(((HAL,Structured Text)))
A HAL component can be written in IEC 61131-3 Structured Text instead of the
`.comp` language. `modcompile` accepts a `.st` file wherever it accepts a
`.comp` one, and produces the same loadable module, the same man page and the
same HAL surface. Nothing else in the toolchain distinguishes them.

The reason to reach for it is that Structured Text is what PLC programmers
already write, and that a `.st` component is checked rather than trusted: the
compiler resolves every name and type before emitting anything, so a mistake
becomes a message with a line number instead of a C error in generated code
nobody keeps.

== A first component

[source,pascal]
----
{attribute 'summary' := 'Two-input AND gate'}
{attribute 'license' := 'GPL'}

PROGRAM and2
  VAR_INPUT
    in0 : BOOL;
    in1 : BOOL;
  END_VAR
  VAR_OUTPUT
    out : BOOL;
  END_VAR

  out := in0 AND in1;
END_PROGRAM
----

Build it exactly as a `.comp`:

----
modcompile --compile and2.st
sudo modcompile --install and2.st
----

That gives a component `and2` with pins `and2.in0`, `and2.in1` and `and2.out`,
and one HAL function `and2` to add to a thread.

== What maps to what

The component's name comes from the filename, as it does for a `.comp`. Inside:

[cols="1,3"]
|===
|`PROGRAM` | one exported HAL function
|`VAR_INPUT` / `VAR_OUTPUT` / `VAR_IN_OUT` | `in` / `out` / `io` pins
|`VAR` | per-instance state, private to the component
|`AT %I` / `%Q` / `%IO` | a HAL pin, at any depth
|`AT %MRW` / `%MR` | a HAL parameter, at any depth
|`VAR_GLOBAL` | per-instance state shared between the programs of one file
|`FUNCTION_BLOCK` | a reusable sub-component with state, internal to the file
|`FUNCTION` | a stateless helper, callable from an expression
|`TYPE` | enumerations, structures and aliases
|`ACTION` | a named piece of a POU's body, sharing its variables
|`USING` | make another `.st` file's declarations visible
|===

An underscore in a name becomes a hyphen on the pin, so `max_rate` is
`comp.max-rate` — the same transform a `.comp` pin name gets.

A variable, pin, parameter or struct field keeps its name in the generated
module, so it may not be one C would read as something else: `int`, `static`,
`long` and the rest are refused by name, as is a leading double underscore.
Types, function blocks, enumeration constants and actions are decorated on the
way out and carry no such restriction.

=== Types

HAL has five scalar types and its `float` is a `double`, which decides what may
appear on a pin:

[cols="1,2,2"]
|===
|Structured Text |On a pin |Elsewhere

|`BOOL` |`bit`, exactly |
|`DINT` / `UDINT` |`s32` / `u32`, exactly |
|`LREAL` |`float`, exactly |
|`SINT` `INT` / `USINT` `UINT` |`s32` / `u32`, widened |
|`REAL` |`float`, with a warning |accepted
|enumeration |`s32` |
|`ARRAY [0..n] OF` scalar |an array pin, one dimension |any shape
|`TIME` |`s32`, in milliseconds |accepted, a duration in nanoseconds
|`DATE_AND_TIME` `DATE` `TIME_OF_DAY` |not possible |accepted, convert to reach a pin
|`LINT` `ULINT` `STRING` `STRUCT` |not possible |accepted
|===

`REAL` reaches a pin without loss but not back, because HAL carries it as a
double. The compiler accepts it and says so; use `LREAL` for an exact pin.

=== Mapping a pin explicitly

Any variable may name the pin it maps to, which is how a component gets a pin
whose name differs from the variable, or a pin from inside a function block:

[source,pascal]
----
PROGRAM mycomp
  VAR
    enable AT %I       : BOOL;    (* mycomp.enable *)
    out    AT %Q       : LREAL;   (* mycomp.out    *)
    fault  AT %Q.alarm : BOOL;    (* mycomp.alarm  *)
  END_VAR
----

`%I` means HAL writes and the body reads; `%Q` the reverse; `%IO` both. The pin
name defaults to the variable's own and is written out only where the two
differ.

This is deliberately not IEC's located-variable syntax, which it resembles.
`%QX0.0` is a physical address, and there is no physical address space here —
HAL signals are the addressing scheme — so `%Q` names a direction and nothing
else. An address-shaped clause is refused rather than reinterpreted.

Inside a `FUNCTION_BLOCK`, an `AT` variable becomes a pin on every instance,
named by the path that reaches it: an instance `r` of a block declaring
`pos AT %Q.position` gives `mycomp.r.position`.

== Parameters

A parameter is a value in shared memory that no HAL signal connects to. `%MRW`
is a tunable you set from outside and the component reads; `%MR` is a
diagnostic the component writes and you can only read:

[source,pascal]
----
PROGRAM mycomp
  VAR
    gain      AT %MRW      : LREAL := 1.0;   (* mycomp.gain, rw      *)
    saturated AT %MR       : BOOL;           (* mycomp.saturated, r  *)
    err       AT %MR.error : LREAL;          (* mycomp.error, r      *)
  END_VAR
----

----
setp mycomp.gain 2.5
show param mycomp.*
----

The `:=` value is the parameter's default, applied when the component loads.
Everything else works as it does for a pin: the name after the dot renames it,
and a parameter declared inside a `FUNCTION_BLOCK` becomes one per instance,
named by the path that reaches it.

An `rw` parameter cannot be assigned in the body, for the same reason an input
pin cannot: you are its writer. To clamp a tunable, read it and keep the
clamped value in a `VAR`. A parameter is a single value — there is no array
form.

== Durations

`TIME` is a duration, written the way IEC writes one:

[source,pascal]
----
VAR
  pt      : TIME := T#500ms;
  warmup  : TIME := T#1m30s;
  elapsed : TIME;
END_VAR
----

The units are `d`, `h`, `m`, `s`, `ms`, `us` and `ns`, largest first, and only
the first may overrun its own unit — `T#25h` and `T#90s` are durations,
`T#1m90s` is a typo. A fraction is allowed on the last magnitude, so `T#0.5s`
works.

A duration is not a number, so `pt + 1` is refused — one what? What is allowed
is what has one meaning: durations add, subtract and compare with each other,
scale by a plain number, and divide by each other to give a ratio.

[source,pascal]
----
elapsed := elapsed + SECONDS_TO_TIME(fperiod);
expired := elapsed >= pt;
half    := pt / 2;         (* a duration *)
ratio   := elapsed / pt;   (* an LREAL   *)
----

=== Converting

stratuMAK holds a duration as nanoseconds, but CODESYS holds one as
milliseconds — so every conversion with an IEC name is in milliseconds, and
computes exactly what it computes in CODESYS:

[source,pascal]
----
ms := TIME_TO_DINT(T#1s);      (* 1000 *)
pt := DINT_TO_TIME(1500);      (* T#1s500ms *)
----

Seconds are what the rest of stratuMAK works in — `fperiod` is seconds, and so
is any float pin carrying a time — so they have their own pair of names, which
cannot be mistaken for the IEC ones:

[source,pascal]
----
secs := TIME_TO_SECONDS(T#1s);   (* 1.0 *)
pt   := SECONDS_TO_TIME(0.25);   (* T#250ms *)
----

=== Points in time

`DATE_AND_TIME` (`DT`) is a point in time, where `TIME` is a length of one:

[source,pascal]
----
VAR
  started : DATE_AND_TIME := DT#2026-08-26-08:30:00;
  due     : DATE_AND_TIME;
  taken   : TIME;
END_VAR

due   := started + T#1h30m;      (* a point moved by a duration *)
taken := due - started;          (* the duration between two points *)
late  := MONOTONIC > T#0s;
----

They are two types because the arithmetic differs: two points subtract to the
duration between them, a point and a duration add to another point, and two
points cannot be added at all — twice last Tuesday is not a time.

`DT_TO_UDINT` and `UDINT_TO_DT` convert in seconds since 1970-01-01 UTC, as
CODESYS does; `DT_TO_SECONDS` and `SECONDS_TO_DT` are the same in `LREAL`, and
`DT_TO_LINT` and `LINT_TO_DT` are the signed form, which reaches the days
before 1970.

=== Days and times of day

A point in time has two halves, and each is a type of its own. `DATE` (`D`) is
a day; `TIME_OF_DAY` (`TOD`) is a position within some day, without saying
which:

[source,pascal]
----
VAR
  today : DATE := D#2026-08-26;
  shift : TIME_OF_DAY := TOD#08:00:00;
  now   : DATE_AND_TIME;
END_VAR

now := today + shift;            (* a day and a position in it: a point *)
----

`DT_TO_DATE` and `DT_TO_TOD` split a point back into them. The split is exact
on both sides of 1970 — a day before the epoch is a negative number, and the
clock still runs forwards through it:

[source,pascal]
----
started := DT_TO_TOD(stamp);
if started >= TOD#08:00:00 AND started < TOD#17:00:00 then
  ...
----

What each half can do follows from what it measures. Two days subtract to the
`TIME` between them, as two points do. Two times of day likewise. A day plus a
time of day is a point in time, in either order. Everything else is refused,
including the one people reach for — a duration added to a time of day, where
23:00 plus two hours is one in the morning of a day a `TIME_OF_DAY` does not
have. Add it to the point in time instead, which does.

`DATE_TO_UDINT` and `UDINT_TO_DATE` convert in seconds since 1970-01-01 UTC,
like the point in time a day is; `DATE_TO_LINT`/`LINT_TO_DATE` and
`DATE_TO_SECONDS`/`SECONDS_TO_DATE` are the signed and floating forms.
`TOD_TO_UDINT` and `UDINT_TO_TOD` convert in milliseconds since midnight,
which is what CODESYS holds a `TIME_OF_DAY` in, and `TOD_TO_SECONDS` and
`SECONDS_TO_TOD` are seconds in an `LREAL`.

=== Durations and HAL

A `TIME` can be a pin or a parameter. HAL has no duration type, so it is
carried as an `s32` of *milliseconds* — which is exactly what a CODESYS `TIME`
is, so a number set from outside means there what it means here:

[source,pascal]
----
VAR_INPUT
  pt : TIME := T#500ms;    (* comp.pt, an s32; setp comp.pt 500 *)
END_VAR
----

The body still works in nanoseconds; the conversion happens where the pin is
read and written, once a cycle, not at every use. A duration finer than a
millisecond does not survive the trip, and the compiler says so at the
declaration.

Where that rounding matters, carry seconds on an `LREAL` pin instead and
convert explicitly:

[source,pascal]
----
delay := SECONDS_TO_TIME(delay_s);
----

== Strings

A `STRING` holds a fixed number of characters, declared with it:

[source,pascal]
----
VAR
  label : STRING[32];
  unit  : STRING[8] := 'mm';
END_VAR

label := unit;                   (* copied, not aliased *)
----

Assignment copies within the destination, because the two need not be the same
length. A copy that loses characters is counted and logged rather than passing
quietly. Two strings compare with `=`, `<>`, `<` and the rest, character by
character and regardless of their declared widths.

A `STRING` cannot be a pin — HAL has no string type — so it lives inside the
component, which is where a message being assembled belongs.

=== The string functions

IEC's own, all of them:

[source,pascal]
----
n     := LEN(label);                 (* how many characters *)
p     := FIND(label, 'mm');          (* where, one-based, or 0 *)

part  := LEFT(label, 4);             (* the first four *)
part  := RIGHT(label, 4);            (* the last four *)
part  := MID(label, 4, 2);           (* four, starting at the second *)

msg   := CONCAT('drive=', unit);     (* two or more, in one call *)
msg   := INSERT(label, '-', 3);      (* '-' after the third character *)
msg   := DELETE(label, 2, 3);        (* two characters out, from the third *)
msg   := REPLACE(label, 'mm', 2, 3); (* two replaced by 'mm', from the third *)
----

Positions are IEC's, so they count from one. A position or a length outside the
string gives what is there rather than an error: `LEFT(s, 20)` on a shorter
string is how you ask for _up to_ twenty, and is not a fault.

Each result is built in a buffer the call site owns, sized from the arguments,
so calls nest as they read:

[source,pascal]
----
msg := CONCAT(CONCAT('drive=', unit), ' ready');
----

That buffer is capped at 255 characters, which is where CODESYS caps a result
too — so a result that outgrows it is truncated in the same place, and the
truncation is counted and logged.

== Function blocks

A function block is a reusable piece with its own state. Its inputs and outputs
persist between calls, so reading an output reads what the last call left there:

[source,pascal]
----
FUNCTION_BLOCK Ramp
  VAR_INPUT
    target : LREAL;
    rate   : LREAL;
    dt     : LREAL;
  END_VAR
  VAR_OUTPUT
    out : LREAL;
  END_VAR
  ...
END_FUNCTION_BLOCK
----

An instance is declared like a variable and invoked as a statement, then its
outputs are read:

[source,pascal]
----
VAR
  r : Ramp;
END_VAR

r(target := setpoint, rate := 10.0, dt := fperiod);
position := r.out;
----

`MONOTONIC` is the real-time clock, as a `TIME`. Its origin is not defined, so
only the difference between two readings means anything — which is what the
standard library's timers are built on.

`fperiod` is the period in seconds of the thread the body is running in. It is
available in a `PROGRAM`, in a `FUNCTION_BLOCK` and in an `ACTION`, and a block
that uses it sees whichever thread it is actually running in — so the same
block added to a 1 kHz thread and a 100 Hz one gets the right answer in both.

It is not available in a `FUNCTION`. A stateless function that depended on the
rate of whatever thread called it would not be stateless; take the cycle time
as an input instead, as IEC's own `DERIVATIVE` and `INTEGRAL` do.

An instance has no HAL identity unless one of its variables carries an `AT`
clause, so instances nest, and an array of them costs nothing special.

== Splitting a body with ACTION

An `ACTION` is a named piece of a body that shares the variables around it:

[source,pascal]
----
PROGRAM mycomp
  VAR_INPUT
    enable : BOOL;
  END_VAR
  VAR_OUTPUT
    count : DINT;
  END_VAR

  IF enable THEN
    advance();
  ELSE
    stop();
  END_IF;

ACTION advance:
  count := count + 1;
END_ACTION

ACTION stop:
  count := 0;
END_ACTION

END_PROGRAM
----

It has no variables and no interface of its own, which is what makes it
different from the two things it resembles: a `FUNCTION_BLOCK` would need every
value it touches passed in and out, and a `FUNCTION` cannot see the POU's
variables at all. Reach for it to break up a long cyclic body without
restructuring what that body operates on.

`advance(count := 0)` is shorthand for setting one of the POU's own variables
before running the action — not a parameter, since an action has none.

A function block can also have `METHOD`s, which differ from an action in
having an interface of their own:

[source,pascal]
----
FUNCTION_BLOCK Accumulator
  VAR_OUTPUT
    total : DINT;
  END_VAR

  (* one of its own methods, on the instance already in scope *)
  add(n := 1, weight := 1);

METHOD add : DINT
  VAR_INPUT
    n      : DINT;
    weight : DINT;
  END_VAR
  total := total + n * weight;
  add   := total;
END_METHOD

END_FUNCTION_BLOCK
----

Calling one on an instance is `acc.add(n := 5, weight := 2)`. Inside the block
— in its body, an action or another method — no name for the instance is
needed, because there is only one it could be; `THIS^.add(...)` says the same
thing in IEC's spelling. `THIS` is not a value: it is a pointer in IEC, and
stratuMAK has none.

A method that returns nothing simply declares no result type, and is called as
a statement. Methods and actions share one namespace within a block, so a name
is one or the other.

An action of a function block can also be called on an instance from outside
it, which is how a block gets commands:

[source,pascal]
----
VAR
  motor : Motor;
END_VAR

motor(setpoint := 1000);
IF fault THEN
  motor.stop();
END_IF;
----

Such a call takes no arguments — an action has no interface. Inside the POU
that declares it, `Act(v := x)` sets one of that POU's own variables first;
from outside there is nothing to set that way.

Actions may also be written after the POU's `END_PROGRAM` or
`END_FUNCTION_BLOCK` rather than inside it, which is how CODESYS exports them.
Both placements mean the same thing.

An action that can reach itself is refused, for the reason any recursion is.

== Libraries

A library is a `.st` holding `TYPE`, `FUNCTION` and `FUNCTION_BLOCK`
declarations and no `PROGRAM`, marked by one pragma:

[source,pascal]
----
{attribute 'library' := 'timers'}
{attribute 'summary' := 'IEC 61131-3 delay timers'}

FUNCTION_BLOCK TON
  ...
END_FUNCTION_BLOCK
----

Name it with `USING`, and what it declares becomes visible:

[source,pascal]
----
USING timers;

PROGRAM mycomp
  VAR
    delay : TON;
  END_VAR

  delay(IN := start, PT := T#500ms);
  running := delay.Q;
END_PROGRAM
----

The file must be `timers.st`, and its `library` attribute has to agree with
that name. A library may `USING` another; a ring of them is refused.

Nothing is dynamically linked. What a library declares is compiled into your
component's own module, so a call to `TON` is an ordinary function call in the
same file, checked against the real declaration, and a fault inside it maps
back to the library's source rather than to yours. Only what you use is
generated, so a library may declare as much as it likes.

=== The standard library

The IEC 61131-3 standard function blocks ship as one library, `standard`:

[cols="1,3"]
|===
|`SR` / `RS` | set-dominant and reset-dominant latches
|`R_TRIG` / `F_TRIG` | rising and falling edge, true for one cycle
|`CTU` / `CTD` / `CTUD` | up, down and up-down counters
|`TON` / `TOF` | delay on and delay off
|`TP` | a fixed-length pulse on a rising edge
|`TONR` | retentive delay on, cleared by `R`
|`SEMA` | a semaphore; `BUSY` says whether the claim was already held
|`BLINK` | a square wave while `ENABLE`
|`LIMITALARM` | above `HIGH`, below `LOW`, or between
|`HYSTERESIS` | a Schmitt trigger with explicit thresholds
|`LIN_TRAFO` | scale linearly from one range onto another
|`RAMP` | slope limiter, at most `ASCEND` up and `DESCEND` down
|`INTEGRAL` / `DERIVATIVE` | integrate and differentiate, over `CYCLE`
|`PID` | a PID controller with anti-windup
|`RTC` | a clock, set from `PDT` and running from there
|===

The analog blocks take the interval as a `CYCLE : TIME` input rather than
reading `fperiod` themselves, which is IEC's arrangement: you decide what
interval the block works over, and `SECONDS_TO_TIME(fperiod)` is the usual
answer.

[source,pascal]
----
dt : TIME;
...
dt := SECONDS_TO_TIME(fperiod);
slope(RUN := TRUE, XIN := position, CYCLE := dt);
velocity := slope.XOUT;
----

The timers take `PT` as a `TIME` and report `ET`, which stops at `PT`:

[source,pascal]
----
delay(IN := start, PT := T#500ms);
running   := delay.Q;
so_far_s  := TIME_TO_SECONDS(delay.ET);
----

They measure elapsed real time, not cycles, so a timer set to 500 ms takes
500 ms whatever thread it runs in and whatever that thread does. If you need
the cycle time itself — for a filter or an integrator — take it as an input the
way IEC's own `DERIVATIVE` and `INTEGRAL` do, and pass `fperiod`.

[source,pascal]
----
USING standard;

PROGRAM mycomp
  VAR
    up  : R_TRIG;
    ctr : CTU;
  END_VAR

  up(CLK := input);
  ctr(CU := up.Q, R := reset, PV := 10);
  done := ctr.Q;
END_PROGRAM
----

These are the standard's own bodies with one difference: IEC declares a
counter's clock as `CU : BOOL R_EDGE`, and stratuMAK does not support that
qualifier — an input that silently becomes a one-cycle pulse is invisible when
you read the body. The counters detect the edge themselves, so `CU` is an
ordinary input and counts one per rising edge either way.

The standard library is LGPL v2.1 or later with an added permission, not GPL,
so a proprietary component may use it. The permission matters: `USING` compiles
the blocks into your own module rather than linking against a separate one, and
the LGPL is written around linking. See `src/hal/st-lib/COPYING`.

`modcompile` looks for `timers.st` in `$STMAK_ST_LIB_PATH` first, then beside
the file being compiled, then in the shipped library directory — so keeping
your libraries next to your components needs no configuration at all. The first
match wins, which is how you override a shipped library with your own copy.

A library cannot declare a `PROGRAM` — there is no component to export a HAL
function from — nor a `VAR_GLOBAL`, which would become per-instance state of
whatever used it. Pointing `modcompile` at a library is refused for the same
reason: there would be nothing to load.

== Several functions in one component

Each `PROGRAM` in a file becomes its own HAL function, with its own pins, and
`VAR_GLOBAL` is what they share:

[source,pascal]
----
VAR_GLOBAL
  latched : DINT;
END_VAR

PROGRAM read
  ...
END_PROGRAM

PROGRAM write
  ...
END_PROGRAM
----

That gives `comp.read` and `comp.write`, addable to different threads. A
function that touches no floating point is exported so it can run in a thread
without floating-point support, which the compiler works out for itself.

Because the programs of one file share a single instance, they may not reuse a
name: two of them declaring `n`, or both exporting a pin called `ready`, is an
error rather than two separate variables.

== Running in the real-time thread

A component runs inside the real-time process, so a fault in one is a fault in
the machine. The compiler enforces what it can:

* **Every loop carries a bound it can see.** `FOR i := 0 TO 7` is bounded by
  construction. A `WHILE`, a `REPEAT`, or a `FOR` whose limit is not constant
  needs one written out:
+
[source,pascal]
----
{attribute 'max_iterations' := '50'}
WHILE NOT settled DO
  ...
END_WHILE;
----
+
Exceeding the bound leaves the loop and records a fault rather than stalling
the thread until the watchdog fires.

* **A subscript the compiler cannot see is clamped.** One it can see is checked
  when you compile, because an index outside its bounds is a mistake rather
  than something to handle.

* **Integer division and `MOD` are guarded.** A zero divisor yields zero and
  records a fault; unguarded it would raise `SIGFPE` and take down the whole
  process.

* **Recursion is refused.** The stack depth cannot be bounded.

Faults are counted per instance and logged at most occasionally, because one
repeating every cycle would flood the journal and become the problem itself.

== Documentation

The pragmas before the first declaration describe the component and become its
man page:

[source,pascal]
----
{attribute 'summary'     := 'Limit how fast a value may change'}
{attribute 'description' := 'Follows target at no more than ...'}
{attribute 'license'     := 'GPL'}
{attribute 'author'      := 'A. Programmer'}
{attribute 'see_also'    := '\fBlimit1\fR(9).'}
{attribute 'notes'       := '...'}
{attribute 'examples'    := 'loadrt ramp$Naddf ramp servo-thread'}
----

A pragma heading a `PROGRAM` documents that program's HAL function, and one
inside a `VAR` section documents the pin it precedes. A value takes the escapes
an ST string does, so `$N` is a line break.

`modcompile --document -o ramp.9 ramp.st` writes the page;
`modcompile --view-doc ramp.st` shows it.

A library is documented the same way, but produces one page per function block
in section 3 rather than one page for the file — a block is what you use:

----
modcompile --document standard.st -o /tmp/pages
man -l /tmp/pages/TON.3
----

The build does this for every shipped library, so on an installed system
`man 3 TON` works directly.

== What is not supported

Structured Text is a large language and this is a subset, chosen so that what
compiles is safe to run in a servo thread. Refused, each by name:

* pointers and `REFERENCE TO` — pass the value through a `VAR_IN_OUT`, which is
  the IEC mechanism for reaching a caller's data
* located variables (`AT %IX1`), and `VAR_CONFIG` — there is no physical address
  space to locate a variable in
* the bit-string types `BYTE`, `WORD`, `DWORD` and `LWORD`, and so partial
  access (`word.0`)
* `WSTRING`, and `STRING` on a pin — see <<sec:st-strings,Strings>> for what a `STRING`
  variable does. It may be a function block member, a struct field, an array
  element or a parameter, though a parameter is a view of the caller's
  characters and cannot be assigned, and no function or method may return one,
  because C returns no arrays — which is why the string functions build their
  results into a buffer instead.
* the other IEC languages — Ladder, Function Block Diagram and Sequential
  Function Chart

== A worked example

The following limits how fast a value may change. It shows a function block
used from a program, per-pin documentation, and `fperiod`.

[source,pascal]
----
include::ramp.st[]
----
